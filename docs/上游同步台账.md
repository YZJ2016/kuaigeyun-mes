- ⚠️ 2026-10-21 起有效新手法：上游 `build-web sync` 提交携全量 dist blob，HTTPS/SSH 普通 fetch 与浅克隆都会在 pack 尾部超 gitee deadline（curl 56/early EOF/DeadlineExceeded）。**用半克隆 fetch**：`git fetch gitee develop --filter=blob:none`——只传 commit+tree（小包），blob 按需惰性回源；代价是离线看历史 blob 会触发回源拉取。fetch 后若 `gitee/develop` 报 non-fast-forward，先 `cat .git/FETCH_HEAD` 拿真实 tip 再 `git update-ref refs/remotes/gitee/develop <tip>`
- 下次同步（2026-10-16 起改用手法）：上游会 rebase 已发布提交产生 patch 等价的平行链，勿逐笔手算 patch-id——

  ```bash
  git fetch gitee develop --filter=blob:none                # 见上条：普通 fetch 会被 dist 大包拖死
  git cherry -v f4f524eda0 gitee/develop                     # 业务提交分类：`+`=新提交需逐笔评估 / `-`=与已评链 patch 等价（rebase 重复），跳过
  git log --oneline --merges f4f524eda0..gitee/develop       # merge 不产生 patch-id、cherry 不显示，须单独扫；有怀疑用 `git diff <merge>^2 <merge>` 验合入结果
  ```

  评估边界按对称差集可达性计算：上游快进或再 rebase 出平行链时命令不变。`-` 判定的安全方向：rebase 中改过内容的提交 patch-id 会变、落到 `+` 侧重新评估，不会漏跳。需要逐对看 rebase 映射/被改动了哪些行时用 `git range-diff <旧段> <新段>`（模糊配对，`=`相同/`!`改过/`+`全新）。每轮同步收尾把 `git cherry` 上游参数更新为本轮 tip
