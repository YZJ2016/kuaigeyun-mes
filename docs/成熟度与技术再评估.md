## 总评

**从「单据型 MES」跨进了「纪律型 MES」门槛，但工程卫生追不上功能面。**

综合成熟度 **3.6 / 5**（约 72 分）。

两个月内质变集中在三处：

1. **闸门真的卡了。** 无检验策略默认必检（IQC/FQC/OQC 全覆盖，含委外收货）；过程检验 `simple`/`plan` 模式未放行不计入转下道与完工；让步必须有已处理不良单；无 BOM 拒绝下达；读不到仓储开关拒绝过账。
2. **账实一致性收紧。** 库存增减强制幂等键（包装层可合成）；序列号有单据留痕台账，撤回只追加反向留痕；库存与业财同一成败；单据关系收口到 `document_relation_new_service` 单一写入口。
3. **三端补齐。** 移动端 uni-app x 五个作业域 51 页；工位机 Electron 壳 + 开工/快捷报工/安灯/人脸交接班；PC 端 574 个 kuaizhizao 页面。

另一面：仓库内无 CI；`warehouse_service.py` 已 17.5k 行还在长；测试套件一度腐化到 84 个失败 + 18 个收集错误，本轮全量甄别后已复绿（2370 过 / 18 跳过），其中揪出 1 处被上游合并带回的真回归（spec 142 工资兜底，已修复）。**能力面到 3.6，工程可信度仍卡在「证据链不完整」：测试绿了但没有 CI 守门，部署手验也未收口**——README 自己也这么写。

## kuaiiot 专项复检（2026-10-07）

本轮确认的新增闭环：

- core 公共连接成为地址与凭据来源；kuaiiot 只保存关联和数采映射，停用、跨租户与引用关系均有约束。
- MQTT 增加实例所有权、订阅租约、续租、配置指纹热重载和失租退出；Agent 增加 SQLite 缓冲、配置热更新与指令结果恢复。
- 趋势和通知改为落库投递，具有投递键、退避重试和待投递诊断；告警包含触发、恢复、确认、处置和业务通知接线。
- OEE 开始按数采状态段、生产数量、良品数、理想节拍和计划生产窗口使用同一计算器；无覆盖时显式返回不可用原因，不再用默认每天八小时冒充计划时间。
- 原评估所写 `test_device_equipment_bind` 腐化已经修复。命令 `PYTHONPATH=src:. uv run --no-sync pytest tests/apps/kuaiiot -q -p no:cacheprovider` 本轮实跑为 **138 passed、363 warnings、exit 0**；只设 `PYTHONPATH=src` 会因测试间导入 `tests.apps...` 出现 3 个收集错误（后续已修：`pyproject.toml` 配 `pythonpath = ["src", "."]`，裸 `uv run pytest` 即可）。

仍需收口：

1. `/apps/kuaiiot/tags` 独立入口只显示点位表单，却没有已有设备选择器；路由重载后 `deviceId` 为空，提交只能提示先登记设备。数采中心同页刚建设备时可继续操作，独立菜单流程则中断。
2. 持久投递没有最大重试与 `failed/dead-letter` 终态；未配置通知规则的 `blocked` 行仍会反复检查。外部趋势/通知调用位于数据库行锁事务内，慢调用会延长锁持有，外部成功而本地提交失败时还需依赖下游幂等。
3. 页面入口与作业层次不完整：趋势、模板、分组、指令和消息主要靠页内文字链接；新增、下发、处置按钮未按动作权限提前隐藏或禁用，虽然后端 RBAC 能拒绝越权，但用户在点击后才得知无权。
4. 多数页面不自动加载、表格关闭分页、提交按钮缺独立 busy 状态，状态以原始字符串或 JSON 呈现；硬编码中文未接平台 i18n，密集 inline 表单也未证明窄屏可用。
5. Edge Agent 仍只有 Modbus TCP 参考实现。OPC UA、Modbus RTU、S7、EtherNet/IP、网关远程升级、多实例 HA、长期断网补传和百万点位容量均没有代码或运行证据。

## 车间主链路复检

### 1. 计划下达
销售预测/订单 → 统一需求 → MRP 净需求 → 工单。下达前缺料检查命中拦截级别即拒绝，**无 BOM 也拒绝**（KR-PG1，代码已核）。计划员仍缺有限产能排程，但「能不能开线」的物料侧已有硬闸。

### 2. 备料发料
领/退料、配料中心、波次拣货、线边仓、倒冲、FIFO 策略齐全。来料入库 IQC 闸：`inbound_inspection_required` 统一判定，采购/客供/委外同一规则，无策略必检。

### 3. 工位作业
工位机开工/暂停（原因码）/快捷报工/SOP 换版确认/上岗资质检查/安灯四类/人脸交接班。移动端扫码报工覆盖离岗场景。**上料强制扫码**仍不是硬约束（绑定可做，不强制）。

### 4. 过程质量
IPQC 三档策略落地：方案模式按检验放行数转下道；**简易模式不再凭报工合格数蒙混完工**（KR-PG6，代码已核 `resolve_operation_transfer_qualified`）；让步接收必须挂已处理不良单。检验NG开始有牙。

### 5. 完工入库
末道产出按检验放行口径；成品入库 FQC 闸、销售出库 OQC 闸（`assert_oqc_before_sales_delivery_confirm`）；序列号写单据留痕台账；库存与成本/应付同一事务成败（KR-PG5/176）。

### 6. 发运售后
送货单、销售出库、退货、售后工单/派工/备件/结算，质量投诉可回追批次。追溯图服务存在，单件级多级族谱仍是半吊子。

## 技术评估

### 栈与结构
FastAPI 0.115 / Pydantic 2 / Tortoise ORM / aerich / PostgreSQL 15 + pgvector（HNSW）/ Taskiq（无 Redis）。前端 React 18 + AntD 6 + Vite 5；移动 uni-app x 蒸汽模式；工位 Electron 44。应用插件化：`src/apps/*` 各带 `manifest.json`，`kuaiems`/`kuaipd`/`kuaiqms` 是壳（业务实居 kuaizhizao）。

### 做得实的
- **租户隔离是机制不是约定**：`TenantEnforcedQuerySet` 三态上下文，读与 queryset 写都强制组织条件，超管跨组织显式且审计（spec 143）。
- **权限码真生效**：约 660 处 `require_permission_codes`，移动工作台条目按权限过滤。
- **一致性收口**：幂等键签名级强制 + 合成兜底、序列号行锁同事务、业财同成败、单据关系单一写入口、检查失败拒绝而非放行。
- **迁移纪律**：912 个 aerich 文件按 14 位时间戳续编，私有仓段不撞开源序号（外层 AGENTS.md 已立规）。
- **部署链路**：fast-deploy 8 阶段向导（Linux/Windows）、Caddy 反代、备份调度（含租户隔离修复与堆积回收）、构建溯源、可选遥测开关。

### 工程债（按痛感排）
1. **测试套件已复绿，但防腐仍靠人肉。** `PYTHONUTF8=1 uv run pytest` 实跑 2370 过 / 0 失败 / 18 跳过 / 0 收集错误。84 失败 + 18 收集错误已全量甄别：1 处真回归（spec 142 工资兜底被上游合并回退为 `Decimal("30")`，已恢复为 `None` + 「未配置」），1 处切片越界手写 SQL（`share_grants` 清理下沉回 s149 切片），其余为 mock 边界腐化、陈旧断言、Windows GBK 编码噪声与缺失生成物（`lexicon.pack`）。`pyproject.toml` 已配 `pythonpath = ["src", "."]`，裸 `uv run pytest` 可直接收集运行；Windows 下跑源码巡检类测试仍需 `PYTHONUTF8=1`（或测试统一显式 `encoding="utf-8"`），建议落入 CI 环境变量。
2. **仓库内无 CI**（无 `.github/workflows` 等）；验证命令问题已缓解（`pythonpath` 已入 `pyproject.toml`），但没有流水线意味着腐化仍会卷土重来。
3. **上帝服务继续膨胀**：`warehouse_service.py` 17,484 行、`work_order_service.py` 9,031 行、`demand_computation_service.py` 6,946 行。已拍板不拆，但每个新闸都往里堆，冲突与回归半径持续变大。
4. **上游 fork 合并成本**：本仓是 `kuaigeyun/kuaigeyun-mes` 的私有 fork，定期 merge upstream；私有修补与上游演进的分叉风险长期存在。
5. **前端构建警告成堆**：i18n 重复 key、AntD Pro 系列循环 chunk 重导出、lottie `eval`、main bundle 约 6MB。`npm run build` 实测可通过，但警告量说明没有 lint 门禁。
6. **Pydantic v1 `@validator` 残留**（master_data 等处，616 条警告）。
7. **「代码已落、部署手验仍开」积压**：多个 spec 标注生产环境手工验证未做，功能在真实部署上的表现没有证据闭环。

## 适用边界

### 适合
10–200 人离散制造，按单/按库混合，要一套覆盖销售-计划-执行-质量-仓储-设备-财务的渐进式系统；愿意用平板/手机报工；ERP 是金蝶系最顺。

### 现在仍不要承诺
- 「开箱即生产」——README 自己声明仅供预览评估，测试与手验证据不足。
- 汽车/医疗级单件全族谱追溯——有序列号单据台账，不是多级投料族谱。
- 任意 ERP 即插即用——集成是金蝶苍穹+推送服务形态。
- 生产级设备数据自动采集闭环——代码主链已接通，但 edge-agent 真机、长稳、HA、断网与 OEE 端到端仍未实证。
- SPC 过程控制、真 APS——只有壳与规则引擎。

## 结论

对比上轮 Java 基座的 2.7，本仓在业务面不是同一量级：闸门、幂等、业财同成败、租户强制隔离、三端都落了代码。kuaiiot 也不再只是「设备数据入口」：可靠投递、连接租约、Agent 恢复、通知和 OEE 口径已经补进主链，代码成熟度可从 3.0 调到 3.5。按 ISA-95 口径，整套系统已经不是「单据型 MES」，但也还没到可拍胸脯的「纪律型 MES」——差的是证据链：部署手验、真机真库跑批、CI 守门，以及 kuaiiot 从工程配置页到生产运营台的收口（全仓测试复绿本轮已闭环）。把剩余 P0 做完，3.6 才是可信的 3.6，并具备单厂试点条件；再往后扩 SPC/APS/多协议数采才有意义。
