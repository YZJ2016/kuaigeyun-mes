评分使用 1–5 分：1 为登记或壳，2 为局部功能，3 为主要流程已有实现但存在闭环缺口，4 为规则和一致性较强，5 为代码层面的完整闭环与可靠恢复。评分是架构与产品判断，不是功能完成百分比，也不是上线验收；3.5 分不能自动解释为“单厂可上线”。

主要约束是：门禁可绕过、不同入口使用不同业务口径、事务提交后的同步或外部写入没有可靠恢复，以及部分展示关系强于实际证据。具体落点统一列在“本轮筛查出的具体问题”章节。

## 业务主链路评估

### 1. 销售、需求与计划

销售订单可下推需求和工单，MRP 有库存、预留、在途、安全库存等净需求计算因素，排程已使用日历与资源容量。主要断点是销售变更在订单生效后才同步需求，失败可能留下订单与计划输入不一致。排程能力不再描述为“产能只展示”，但全局优化与资源并发保存仍不能据静态局部阅读作承诺。

### 2. 下达、备料与工位开工

下达缺料检查受业务配置和 `ignore_shortage` 控制，无 BOM 拒绝位于同一可跳过分支，不能称为不可绕过的硬闸。领料、线边仓、批次与库存过账已有实质控制。工位操作员会话验证身份、权限和工位一致性；技能资质与 SOP 确认虽然有前端流程，但未成为已读后端开工链路中的统一门禁。

### 3. 报工、过程质量与完工

普通报工、转下道与主要末道产出链路使用检验放行口径；`simple`/`plan` 并非只看报工合格数。工位“结束工序”仍直接比较工序合格数，状态报工还直接赋目标数量。应区分“工序状态完成”与“检验放行可产出”；当前入口间不一致，不等于已证明最终入库可绕过 FQC。

### 4. 入出库与财务

库存余额、流水、批次、序列号与单据互斥保护较强，FQC/OQC 也有确认闸门。采购、销售和财务之间有真实接线，但总账、预付生成等路径的事务与恢复强度不同。库存一致性不能被推广为整个财务领域已同成败。

### 5. 研发到生产

阶段门、交付物审批、生效版本与生产文件下载可见性已有控制；项目也能生成试制工单。工程变更 ERP 稽核回填、BOM 协同录入仍主要是协同状态与引用，不等于生产 BOM、在制工单和现场文件已全部完成受控变更。

### 6. 数采、追溯与管理分析

数采入站具有设备行锁、持久去重、乱序快照保护；MQTT 有租约，Agent 有本地缓冲和指令结果恢复。OEE 使用明确计划窗口、理想节拍、状态段、产量和良品数；覆盖不足会返回不可用原因，未用固定八小时替代计划。仍需注意历史写入与持久趋势投递是两套路径。追溯图和报表已可用作调查与分析入口，但推导关系和错误合计会影响决策可信度。

## 技术评估

### 栈与结构

后端沿用 Python 3.11、FastAPI 0.115 系列、Pydantic 2、Tortoise ORM 0.21.1、aerich 0.7.1、PostgreSQL 与 Taskiq；PC 使用 React 18、Ant Design 6、Vite 5，移动为 uni-app x，工位壳为 Electron。应用按 `src/apps/*` 组织，工位业务页面在 PC 工程内，移动业务调用现有后端。这里依据依赖声明与代码结构，不代表实际部署版本检测。

### 机制与覆盖边界

- `stock_posting.py` 用 PostgreSQL 事务 advisory lock 串行同键过账和同单据操作，流水命中避免重算，并显式复用外层事务。这是库存评分较高的依据。
- `TenantEnforcedQuerySet` 对受管模型查询和 queryset 写注入租户条件，无上下文失败关闭；源码同时声明 `raw()`、M2M、实例级 save/delete、create 自动写租户等不由该机制全面覆盖。不能把这项机制写成所有访问路径天然安全。
- 动作权限、财务路由动作映射、移动工作台过滤、工位操作员会话和 AI 工具 guard 都有实际接线。客户端来源头不能替代服务端身份或动作授权。
- 通用 API 幂等是进程内 TTL 缓存；库存是数据库级幂等；移动持久提交服务虽已存在，却未接入已核快捷报工入口。三者不能混称为全系统持久幂等。
- 私有迁移规则要求新文件首段使用递增的 14 位时间戳。历史迁移仍有整数序号，不再写成“全部迁移均按时间戳编号”。

### 工程可信度与历史验证

1. 本轮仓库范围未检出常见 GitHub/GitLab/Jenkins CI 配置；这不证明仓外没有流水线，但仓内看不到自动验证门禁。
2. PC 的 `build` 脚本是 Vite build 后移动产物，没有在该脚本中串接 `tsc` 或 lint；安装了检查依赖不能替代执行证据。
3. 仓储、工单、质量、MRP 等服务仍是大型文件，跨领域调用较多，合并和回归半径大。不在本评估中自行选定拆分方案。
4. 已有 PostgreSQL 库存事务回归代码；未配置专用 `INVENTORY_TEST_DATABASE_URL` 时会跳过。普通 pytest 通过不能自动证明该部分实库并发已验证。
5. 历史文档记录后端 `PYTHONUTF8=1 uv run pytest` 为 2370 passed、18 skipped，IoT 专项为 138 passed；历史前端 build 记录为通过，并有 i18n/chunk/eval 等警告。这些是历史记录，本轮未重新执行，不能认证 `678b47a524`。
6. `pyproject.toml` 已配置 `pythonpath = ["src", "."]` 和 asyncio 模式；依赖与测试配置存在不等于当前套件全绿。历史 Windows 编码和 Pydantic 迁移告警数也不作为本轮实测数。
7. 部署、备份恢复、真机、多进程、真实 ERP 对账的历史未验证项仍需独立取得运行证据。本轮没有靠“不启动服务”排除静态可见风险。

## 本轮筛查出的具体问题

下列编号便于后续追踪。P0 表示账务或生产事实一致性高风险，P1 表示关键闭环或恢复缺口，P2 表示能力边界或作业体验限制；它们是评估优先级，不是已批准修复计划。所有项目本轮均未修复。源码位置以文件与符号为准；逻辑推演和并发风险不写成已复现线上事故。

### Q01（P1）下达可跳过缺料及无 BOM 检查

- **代码落点**：`riveredge-backend/src/apps/kuaizhizao/api/productions/work_orders.py::release_work_order`、`services/work_order_service.py::release_work_order`；PC `services/work-order.ts::release` 与工单页继续下达调用。
- **触发与影响**：`ignore_shortage=true` 会令 `check_shortage=False`，无 BOM 拒绝也位于该分支中；配置不拦截时同样不是无条件闸门。
- **判定**：确定的代码路径；是否允许这样放行属于业务决策，不能沿用“无 BOM 永不下达”的结论。
- **后续核验重点**：缺料与结构缺失各自的允许边界、越过检查的授权与留痕。

### Q02（P1）资质与 SOP 确认未形成服务端开工门禁

- **代码落点**：`riveredge-frontend/src/apps/kuaizhizao/station/execution/StationExecutionPage.tsx::runStart`；后端 `work_order_service.py::start_work_order_operation`、`station_service.py::check_operator_skill/check_sop_acknowledged`、`api/deps/station_operator_session.py`。
- **触发与影响**：已读后端开工路径不重核资质和当前 SOP 版本确认；直接调用开工不能依靠前端流程保证这些条件。操作员会话验证的是身份、权限和工位，不等于技能/SOP 合格。
- **判定**：已核调用链的规则缺口；不否定已有身份会话门禁。
- **后续核验重点**：PC、工位与其他开工入口是否共享同一业务条件。

### Q03（P1）工位结束工序与普通报工的质量口径不一致

- **代码落点**：`station_service.py::complete_work_order_operation`、`reporting_service.py::_effective_completion_quantity`、`operation_transfer_service.py::resolve_operation_transfer_qualified`（均在 `riveredge-backend/src/apps/kuaizhizao/services/`）。
- **触发与影响**：工位按 `op.qualified_quantity` 判断数量达标，状态报工直接赋目标合格数；普通报工/转序使用检验放行数量，可能产生“状态完成但未放行”的差异。
- **判定**：确定的口径差异；本轮未证明最终入库必然绕过 FQC。
- **后续核验重点**：工序状态、工单进度、转序和可入库产出的一致含义。

### Q04（P0）总账记账与余额更新缺少统一并发保护

- **代码落点**：`riveredge-backend/src/apps/kuaicaiwu/services/posting_service.py::post_voucher/unpost_voucher`、`gl/balance_service.py::get_or_create_balance/apply_voucher_lines`；API `api/gl.py`；通用 `core/middleware/api_idempotency_middleware.py`。
- **触发与影响**：凭证状态和期间在事务前读取；余额采用读取、Python 累加、save。已读链路未见凭证/余额行锁或条件状态转换，可形成同凭证重复作用、同余额丢失累加的竞态。进程内缓存不能兜底多进程或内部调用。
- **判定**：静态并发风险，未执行并发复现。余额唯一约束也不替代已有行更新的并发保护。
- **后续核验重点**：同凭证双请求、不同凭证同余额、记账与反记账交错、期间关闭并发。

### Q05（P0）结账多步写入缺统一事务且重试可能提前返回

- **代码落点**：`riveredge-backend/src/apps/kuaicaiwu/services/gl/period_service.py::close_period` 与 `balance_service.py::roll_opening_to_next`；直接调用入口 `api/gl.py::close_period`。
- **触发与影响**：先保存关闭状态，再开下期、更新账期、滚动余额；后续失败可留下部分完成状态。重试遇到已关闭期间直接返回 `already_closed`，不继续补齐。
- **判定**：确定的控制流程，故障后果为静态推演。
- **后续核验重点**：每一步故障后的账期、余额和重试结果一致性。

### Q06（P1）追溯图混合真实关系与展示推导关系

- **代码落点**：`riveredge-backend/src/apps/kuaizhizao/services/traceability/graph_assembler.py::build/_append_binding_chain/_append_document_relation_edges`。
- **触发与影响**：时间排序串边、按事件类别连接工单与检验/领料、成品入库连接首个工单，与真实投料和单据关系共同进入图。不能把所有边解释为物料因果、单件谱系或召回范围证据。
- **判定**：确定的组图逻辑及产品证据边界。
- **后续核验重点**：多工单、多检验、多入库时的准确关联和推导边识别。

### Q07（P1）SPC 计算与分组口径仍有限

- **代码落点**：`riveredge-backend/src/apps/kuaizhizao/services/quality_improvement_service.py::SPCService.build_imr_chart`、`inspection_step_spec.py::build_spc_sample_payloads`、`models/spc_sample.py`。
- **触发与影响**：名为 I-MR 的实现使用当前查询值的 `pstdev` 和均值 ±3σ，已读方法没有移动极差计算；控制限随查询样本重算，查询按租户与特性名而非 `sample_group` 分组。新版采样通常在名称中带物料编码，但旧 measurement 路径只用名称，不能声称完全不存在物料区分，也不能声称分组已严谨。
- **判定**：计算与建模边界已确认；完整统计过程控制能力尚未成立。
- **后续核验重点**：控制图命名、基线窗口、同名特性和不同工艺/样本组的数据口径。

### Q08（P1）tag_history 写入失败后可能无法由原键重试补齐

- **代码落点**：`riveredge-backend/src/apps/kuaiiot/services/ingest_service.py::_ingest_matched`、`tag_history_store.py::write_points`、`trend_service.py`。

- **判定**：确定的故障窗口推演，未做 InfluxDB 故障注入。
- **后续核验重点**：已接受快照与历史点对账、异常重试、进程重启后的遗漏恢复。

### Q09（P1）IoT 持久投递在行锁内调用外部服务且无死信终态

- **触发与影响**：锁定投递记录的事务内执行趋势/通知外部调用；慢服务延长持锁，外部成功本地提交失败存在不确定结果。永久失败或规则未配的 pending/blocked 持续重试，未见最大次数与死信终态。
- **判定**：代码结构与状态机边界已确认；规模化性能未实测。
- **后续核验重点**：慢调用、永久失败、外部成功后提交失败、人工核对和重放。

### Q10（P1）销售变更已生效但需求同步失败可被忽略

- **触发与影响**：订单、合同释放量与 APPLIED 先提交；需求同步在事务外，异常被捕获返回 False，调用方未检查；计划影响标记也捕获失败。重试已生效变更直接返回，不能保证补齐。
- **判定**：确定的失败处理路径，未执行故障注入；已读路径未确认持久补偿。

### Q11（P1）销售发票创建成功但单据关系可能缺失

## 适用边界与结论

代码覆盖适合渐进式离散制造管理：以销售/需求驱动计划，结合工单、报工、检验、仓储、设备、财务和研发协同。历史“10–200 人”定位只能作为产品目标，不能作为本轮已验证容量；金蝶相关集成已有积累，但本轮没有实证哪个 ERP 的现场接入效果最好。

当前不能承诺：开箱即生产、所有入口都不可绕过的业务纪律、全系统持久幂等、总账并发与结账全面正确、单件多级族谱与准确召回、复杂多资源全局优化、完整统计过程控制、任意 ERP 即插即用、四端真机稳定发行或大规模数采 HA。

**核心 MES 已形成真实流程，MOM 扩展也有业务价值。下一阶段成熟度提升主要来自统一业务事实、事务与失败恢复，而不是继续增加页面和端点。** 库存过账可作为当前机制强度的参照，但其他领域不能仅凭“调用到了”就判为同等可靠。先处理本轮明确的代码问题，再独立取得运行与现场证据，才能提高对外承诺等级。

- 本轮没有启动服务、运行 pytest/build、数据库迁移、故障注入、性能/并发测试或浏览器交互。
